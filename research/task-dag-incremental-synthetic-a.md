# 增量更新 + 多归属：合成语料 A **4/4 通过**

工具：`node tools/probes/task-dag-incremental.mjs --cut 20`
（前 20 回合出结构 → 给模型"已有结构 + 新的 12 回合"，只要**增量**）
**2 次调用 · 输入 1631 · 输出 950 tokens**

## 四条标准（预先写死）

| # | 标准 | 结果 |
|---|---|---|
| 1 | `#21`（天气）有零散节点 | ✓ `#21 下雨闲聊 [零散]` |
| 2 | `#25–26` **多归属** | ✓ **多归属共 11 个回合**（单趟版本是 **0** 个） |
| 3 | 已有结构不重排 | ✓ `reparent` 为空 |
| 4 | 新回合全覆盖 | ✓ 12/12 |

## 关键发现：**增量这个框架本身让多归属自然出现**

同一场语料、同一个模型：

- **单趟**（一次给全部 32 回合、要求直接出多归属）：**0 个多归属**——
  我把 `#25–26` 当例子写进提示词它都不照做；
- **两趟**（先出结构，再"把新回合接到结构上"）：**11 个多归属**。

⇒ 差别不在措辞，在**任务形状**。单趟时模型在做"划分"这个动作；
两趟时它在做"把这一段接到已有节点上"，而一个回合**同时接两处**是自然的动作。
**使用者"要适配逐渐增加节点"这个要求，不只是产品需要，它同时也是让多归属出现的前提。**

## 但**多归属被过度生成了**（这是新的失败模式）

11 个里我逐个看，**站得住的大约一半**：

| 回合 | 挂到 | 我的判断 |
|---|---|---|
| `#21` 覆盖率+天气 | 覆盖率询问 + 下雨闲聊 | ✅ 真的两件事（含覆盖率确认 + 闲聊） |
| `#25` 缓存目录权限 | 缓存目录位置 + 缓存目录权限配置 | ✅ 一条线的两段 |
| `#26` 日志目录权限 | 日志轮转配置 + 日志目录权限检查 | ✅ 同上 |
| `#22` 脚本其他问题 | 部署脚本权限报错 + 脚本其他问题排查 | ✅ 父与子同时命中（合理） |
| `#23`/`#24` | sudo 两次原因 + sudo 改一次验证 | ⚠️ 这两个本同一件事，**该合并而不是多挂** |
| `#27`/`#28` | 登录重试逻辑 + 刷新 token 测试 | ⚠️ 同一条线（父与子），算合理 |
| `#29`/`#30`/`#31` | staging 部署文档 + 收尾类节点 | ❌ **疑似误挂**：那是前面早就结束的节点 |

⇒ 失败模式**从"从不多挂"翻到了"见相关就多挂"**。
缺的是一条**多归属的判据**——而使用者的原话就是判据：
**"如果同个对话存了**几个任务**的内容"**——是"同时推进两件事"，不是"内容相关"。

## 下一步（若继续）

按这条判据收紧提示词（"只有当这个回合**同时在这两件事上推进**时才多挂；
只是内容相关、或本来就是同一条线的上下级，不算"），再量一次同样的四条标准，
**并加第五条**：多归属的**精确率**（人工看 11 个里几个站得住——上面那张表就是第一次量）。

⚠️ 仍然全部来自**一场合成语料**；而且"多归属对不对"目前**只有我的判断**，
不是使用者的。

# 收紧判据之后：**过度生成减少，但仍没做到交叉线**

收紧后的 `PASS2` 判据（三档）：✅ 同时推进**两条不同线**才算；
❌ 同一条线的父与子、或兄弟，不算；❌ 只是"内容相关"不算。
并要求"**要能说清它在哪两件事上各推进了一步**，说不清就别挂"。

同时**修了一个度量错误**：上一版把"父与子同时命中"也算多归属——那是**结构本身**。
现在报两个数：原始多归属、与**交叉线**多归属（两个节点互不为祖先/后代）。

**结果**（2 次调用 · 1741 输入 · 875 输出）：

    多归属：原始 8 个（上轮 11）· 交叉线 3 个

| 回合 | 挂到 | 口径 |
|---|---|---|
| `#21` 覆盖率确认 + 闲聊天气 | 缓存工期确认 + 下雨闲聊 | ✓ **交叉** |
| `#22` 回到部署看脚本 | 部署脚本权限报错 + 脚本其他问题 | 同级（父与子） |
| `#23`/`#24` sudo 改了吗 / 验证 | sudo 两次原因 + sudo 改一次验证 | ✓ 交叉**（但这两个本该合并，不是多挂）** |
| `#25` 缓存目录权限要不要配 | 缓存选型本地文件 + 缓存目录权限 | 同级 |
| `#26` 日志目录权限也检查 | 日志轮转配置 + 日志目录权限检查 | 同级 |
| `#27`/`#28` 刷新 token 加测试 | 登录重试逻辑 + 刷新 token 测试 | 同级 |

**四条标准**：零散节点 ✓ · **`#25–26` 交叉线多归属 ✗** · 不重排 ✓ · 全覆盖 12/12 ✓

## 结论：收紧有效，但方向不对

- 过度生成**确实减少**（11 → 8），说明判据起了作用；
- 但**使用者真正要的那一处（`#25–26` 同时属于部署与缓存）仍然没有出现**——
  `#25` 只挂在缓存那条线，`#26` 只挂在部署那条线；
- 而三处"交叉"里，`#21` 明显对，`#23`/`#24` 是**该合并却多挂**（另一种错）。

⇒ **提示词这条路到这里了。** 按与使用者的约定，下一步是把这 8 个（或其中关键的 6 个）
**逐条给他标"对/错"**——判据在他那里，模型的输出只是候选。

## 顺带一个发现：模型输出不是严格 JSON

这一轮解析失败的原因**不是截断**（长度才 785），而是 `"nodes":[n6]` ——
**裸标识符没加引号**。已加容错（补引号后再解析），并且**把这件事打出来**，
因为它是同一族问题：模型输出的格式保证比想象中弱
（之前还见过 ```json 围栏、前后夹话）。

## 失败 2（#23/#24 没合并）：**这是我的 schema 的锅，可证明**

**我给的增量 schema 里根本没有"合并"这个操作**——只有
`newNodes` / `memberships` / `reparent`。

而"把两个已有兄弟节点合成一个"**是结构上的修改**，不是新节点、不是改挂、
也不是改归属。**提示词里我写了"要合成一个节点"，但输出格式里没有地方表达它。**
⇒ 模型没法照做，不是它不听话。

**这与前面几次是同一个毛病**：我先定输出形状，再要求模型做形状之外的事。
（上上次：单区间 schema 却要求表达"离开又回来"；上次：单趟划分却要求多归属。）
**三次都是我先限制了表达，再抱怨做不到。**

要修就得加一个操作，例如：

    "merge": [{"from": [3, 7], "title": "sudo 处理"}]

## 失败 4（那四条父子双命中变成单一归属）：**结构性回归**

`#26` 这次被挂进一个新的根 `缓存日志目录权限`，不再同时属于 `日志轮转配置`。
那四条是使用者**判过"对"**的，这次全丢了。

## 更根本的问题：**我一直在拿单次运行比较不同提示词**

每一版提示词我只跑**一次**，然后对比结构。而实测：
- 同一份输入，**判定会翻面**（前面量过 18%）；
- 这里更甚——**整棵树的结构都不稳**（三次运行三个样子：10 根 / 8 根 / 10 根，
  节点数 26 / 9 / 12）。

⇒ **前面所有"改了 X，结果变成 Y"的说法都是单例比较，不足以支持因果。**
要比较提示词版本，每个版本得跑 3 次以上、比**分布**（例如"sudo 节点数"的分布），
而不是比一次的形状。

## 该停下来说清楚的三件事

1. **这一轮的"优化"没有带来改进**，按我自己定的标准反而更差；
2. **其中一条失败是我的 schema 缺操作**（merge），与模型无关；
3. **方法上我一直在单例比较**，所以前面那些"有效/无效"的结论都**偏弱**。

**继续调提示词的价值存疑**——真正卡住的是（a）输出形状的表达力，
（b）评测要有重复次数。两件都不是"再改一句话"能解决的。
