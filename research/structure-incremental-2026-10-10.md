# 结构增量归属：新回合接到已有结构上（实测 5 次调用 → 2 次）

> 上一步把**语义判定**做成了增量（`research/semantic-incremental-2026-10-10.md`）。
> 这一步解决另一半：`/api/intent.structure` 原先按 `会话::contentHash::...` 缓存，
> 而 `contentHash` 覆盖整场内容 ⇒ 新来一个回合就**整场重算**（`f1cd07a6` 实测
> 33 次调用 / 41.7 秒）。这正是使用者那句"新的会话都将是增量的"缺的那一块。

## 做法

```
① 会话级记忆 memo[sessionId] = { 它当时覆盖的那批回合, 那一版结构 }
② 新请求若与记忆里的回合**逐字前缀相同、只是更长** ⇒ 只把多出来的回合接上去
③ 否则（早期回合被改写 / 更短 / 换了会话）⇒ 回退全量
```

- **前缀判据**：`isPrefixExtension`（`shared/taskPipeline.ts`）逐字比较 `turn` 与 `prompt`。
  逐字是有意的：`prompt` 正是折叠时写下的原文，变了就说明这段历史被动过
  （压缩会改写早期 prompt）。那种情况**必须**回退全量——在旧树上叠新枝会得到一棵
  与当前内容不符的树，而且**不会报错**。
- **增量那一段只做归属**：复用 `ASSIGN_PROMPT`（它本来就写着"已有节点清单 + 下面是新增的回合"），
  按 `chunk=12` 分批，一批一次调用。**不跑**建结构、判整理、根裁定——那三段的职责就是重排
  （合并/改名/建项目节点），与"已有结构不许重排"直接冲突。也**不补问**（全量的经验是
  "承接继承才是主力，补问不可靠"）；承接语仍由 `carryForward` 补齐，与全量同一套规则。

### 两条保护（`applyIncrement`）

| 保护 | 防的是什么 | 账目字段 |
|---|---|---|
| `placements` 只认本轮新回合 | 模型顺手把老回合也写一遍 ⇒ 一次增量悄悄改写历史归属 | `ignoredPlacements` |
| `newNodes` 与已有 id 撞名就丢掉 | 撞名会**覆盖**已有节点（标题、父子关系全没） | `collidedNodes` |

两个数都回给面板（`meta`），**不许静默**：长期不为 0 就说明提示词里的约束没被遵守。

## 离线断言（假 llm，不花钱）

`scripts/verify-task-structure.cjs` **11 → 17**：

- 增量：同会话多一个回合只多**一次**归属调用（`mode: 'incremental'`、`calls === 1`），
  build / consolidate / adjudicate 的计数**一个都不涨**；
- 增量：已有节点的 id / 标题 / 父子关系**逐字不变**（逐节点 `deepEqual`）；
- 增量：新回合全覆盖（承接语补齐后 26/26）；
- **回退**：把第 1 个回合的 prompt 改一个字 ⇒ `mode: 'full'`；
- `applyIncrement`：越界落点被丢、撞名新节点被丢、老节点与老回合归属**不许被改写**；
- `isPrefixExtension`：延长=真；改写 / 一样长 / 更短=假。

## 实测（3098 真模型，`d5b0e76c`）

两步走：先只送前 30 个回合（冷跑全量），再多送 15 个回合。

| 请求 | mode | 调用 | 批次 | 耗时 | 节点 | 覆盖 |
|---|---|---|---|---|---|---|
| 前 30 回合 | `full` | 5 | 1 | 4.6 s | 13 | 30/30 |
| 扩到 45 回合 | **`incremental`** | **2** | 2 | **2.2 s** | 16 | **45/45** |

第二份的 `meta`：`addedTurns: 15 · ignoredPlacements: 0 · collidedNodes: 0 · inherited: 4`。

探针 `--compare <上一份快照>` 的断言（7/7 通过）：

```
✓ 已有 13 个节点逐字未变
✓ 这次是增量接上去的（meta.mode）  (incremental)
对照上一份快照：新增节点 3 个（t36、t38、t39…） · 新增回合 15 个 · 继承 4 条
```

**成本形状**：结构那一侧从"每变一次整场重算"变成 **每 12 个新回合 1 次调用**
（≈ 0.08 次/回合）。合上语义判定那一侧的增量，稳态就是使用者说的那个样子：
新会话边聊边长，老的存量各跑一次全量。

顺带解决的两件事：

1. **节点 id 不再漂移**——全量重算会重新生成一套 id，人工调整（B4）随之白改；
   增量下已有节点的 id 恒定。
2. 面板结构不再"每次刷新换一棵树"。

## 这一步**没有**做的（都是已知取舍）

- **增量里不跑判整理与根裁定**：所以新节点不会被合并、改名，也不会因为出现新线而重建项目根。
  长期后果正好是上一轮量到的那个形状——`f1cd07a6` 225 个节点里 171 个只收 1 个回合。
  要收敛得给增量补一次**定期整理**（例如每新增 N 个节点、或新线出现时跑一次判整理 + 根裁定）。
- **压缩会触发全量**：压缩改写早期 prompt ⇒ 前缀不匹配 ⇒ 回退全量（这是**对的**行为，
  不是缺陷，但成本会回到全量那一次）。
- **memo 只在进程内、只记最近一次**：宿主重启后第一次请求仍是全量；同一会话的旧版结构不保留。
  要跨重启复用得落盘（`~/.dsh/storages` 里有先例）。
- 真实会话上只验了 `d5b0e76c` 这一场（30 → 45），**不是分布**；377 回合那场的"再来一个回合"
  只是按同一算法推算（1 批 = 1 次调用），没有实测。
