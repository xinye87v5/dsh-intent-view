## 二、最直接的竞争项：`dsh-requirements-alignment`

736/月 · 8★ · v0.4.2 · `Runtime requirement drift guard`

**它的机制**（从 tarball 里的 README 核实）：

| 组件 | 作用 |
|---|---|
| `establish_baseline` 工具 | 记录基线：`goal` / `explicitConstraints` / `mustPreserve` / `allowedScope` / `userDecisions` |
| `report_drift` 工具 | **由 agent 主动报告**漂移候选，通过官方 user-questions 通道问你一个问题 |
| 系统提示策略段（order 60） | 教 agent 持有基线、只在实质改变方向时出声 |
| `/align` 命令 | 人工查看当前对齐状态 |
| `AlignmentStateStore` 侧车 | 状态**不在会话事件里**，所以 resume/fork/compaction 都能恢复 |

**它自述与 Plan Mode 的分工**（README 原文，这句最值得记）：

> Plan Mode 问"**这个实现计划对吗**"；Requirements Alignment 问
> "**我们还在解决对的问题吗**"。
> *"You decide the direction. The agent decides the engineering."*

**它明确不做**：没有周期性检查、没有工具调用计数、执行期 agent **完全静默**
（除非某步会实质改变基线）。

### 与我们最关键的一处差异

**它的漂移由 agent 自己 report。** 这是一个**协议约束**，不是测量。

而我们这边 `ctx-compression/docs/02` §3.4 的 P1 写着：

> **判据必须可观测，不问模型。** 让压缩器判断"这个任务有蓝图吗"等于让它自己决定该不该丢东西。

⇒ **同一个原则在这里适用**：让 agent 自己报告"我漂移了吗"，等于让它自己决定
该不该承认。我们的做法是**从会话本身算**（`shared/intent.ts`），不经过模型。

1. 把**推断出的意图**展示给用户审阅的通用面板（只有 GoalBar 与两个近似物）

## 一处必须写清的更正

**这份初稿把"独有"说过头了。** 并行子调研（读了源码与官方文档）给出更严的结论：

> **算法层面几乎没有"前所未有"。** 按连续性滑窗切话题 = TextTiling / 词法内聚，
> 1997 年的标准基线，今天仍是对话分段的参照方法。真正稀有的是下面三条……

**真正稀有的三条（按其确信度排序）**：

1. **分组结构本身即度量：不与固定基线比，而与"同组兄弟回合"比。**
   扫过 DSH 全部相关插件、Claude Code / OpenCode 的目标插件、全部商业观测平台：
   **所有漂移检测都是"当前 vs 固定基线"**。以"自动切出的话题组"为基准、
   以"同组其他回合"而非"组目标文本"为参照系——别处没找到。
   *别人没遇到那个"全局 56.2% 低重"的问题，是因为他们没做组内比较。*

2. **把压缩当成"话题转向的混淆源"来校正，而不是当成一个事件来标记。**
   生态里的压缩处理只有两类：(a) 标位置；(b) 测"丢了什么"。
   "压缩会让之后回合与历史的字面重合自然下降，不区分就会把每次压缩误报成转向"
   这个混淆、加上 `turnsAfterCompaction`、窗口内/外两套措辞、琥珀（非红）语义
   ——别处没见过。

   ❌ **已否证（2026-09-23，本项目自己的检验）**：这一条**不成立**。
   见下面「机制被自己的检验否掉」一节。

3. **胶囊式表示法**（确信度低但确实稀有）：概况层每组一行（含**派生**目标 +
   起止回合 + 不贴合数）→ 详情层逐回合贴合度，且**标明目标派生自第几回合**。
   DSH 侧没有插件做"话题组一行 + 组派生目标"——`turnOutline` /
   `conversation-navigator` 都是**逐回合**列表。

### ❌ 机制被自己的检验否掉（2026-09-23）

那条"最确信的独有性"——**把压缩当成话题转向的混淆源来校正**——
建立在一个机制陈述上：「压缩之后，后续回合与历史的字面重合会下降」。
它一直是**推断**，被外部评审指出后我写了一个检验来测它
（`tools/test-compaction-confound.py`，进构建）。

**结果是机制不成立。**

```
               前窗中位 → 后窗中位      后窗更低的比例
压缩点（去重后 19 组）  0.4243 → 0.4334   **+0.0091（上升）**   31.6%
安慰剂（无压缩会话 80 组）0.5415 → 0.5167   −0.0249（下降）      52.5%
```

**方向与机制预期相反**：压缩点之后的重合**上升**，而随机位置反而下降。

**两处必须说清的**：

1. **去重是必需的，而且它翻转了方向。** 24 组里有 6 组是同一会话的副本
   （给出完全相同的 `0.629 → 0.414`），不去重会得出"下降 0.0260"。
2. **置换检验给的 `p = 0.045` 我不采纳**：两组的**位置分布本就不同**
   （压缩点集中在同一回合、安慰剂均匀随机），这个零分布不可信。
   在 `n=19`、方向相反、且判据本身不可靠的情况下，正确结论是**没有证据**，
   不是"p<0.05 所以有"。

**处置（已落地）**：压缩的**位置**照旧显示（那是 `compaction/start` 的事实），
但**不再由它推断转向的成因**——那个推断已从代码里删掉，
措辞从「⚠ 可能由窗口收缩造成」改为「压缩后 N 回合内（**成因未证实**）」。

⇒ 这一条从"最确信的独有性"降为**已否证**。真正剩下的独有性只有
「分组结构本身即度量，不与固定基线比」一条（并附 WindowDiff 的反证）。

### 已补：`WindowDiff` / `Pk` 与一个反证

评审 §6(a) 把这条推得更严：**同算法的第二实现只证明自洽，不证明正确。**
已实现 `scripts/segment-quality.mjs`（进构建），并**先定反证再报数字**：

| 项 | 值 |
|---|---|
| 真值 | 我们自己定义的局部谷底，24 段 · `k=8` · 371 个窗口 |
| **WindowDiff** | **我们 0.4906 · 朴素基线 0.6146**（低 **0.1240**，约 20%） |
| Pk | 我们 0.3989 · 朴素 0.5606 |
| 自反 | `WindowDiff(ours,ours) = 0` ✓ |
| 负对照 | 过度切分 = **1.0000** ✓（判据会变红） |

**反证：若不优于朴素基线，那套连续性算法就是白做的。实测它没有成立。**

> ⚠️ **但这个"更优"有自我循环成分**：真值与算法**同族、同窗口大小**，
> 等于拿自己家的尺子量自己。它仍**不是恒真**（朴素基线在同一把尺子下输了 0.1240），
> 但**不能**证明"分段在语义上是对的"。要判后者需要**人工标注**的分段真值。

**同时否掉了一个不可信的数字**：保守真值（只留最低 10 个边界）会算出
`0.9475 vs 0.9972`，看着也有差——但那个 `k=17` 太大（平均段长 34.5），
几乎每个窗口都跨边界，**判据退化了，那个差没有信息**。脚本现在会显式拒绝这种情形。

### 一条已补的技术债（原）

**没有和任何标准分段基准对过。** grep `src/`、`scripts/`、`research/`、`README.md`：
**WindowDiff / Pk / DialSeg711 / TextTiling 全部 0 命中**，也不报 Pk / WindowDiff / F1。

所以"35 组 / 56 组"只通过了**同一算法的 Python 第二实现的交叉校验**（自洽性），
**不等于分段正确性**。按标准做法，阈值型分段应报 **WindowDiff**（Pk 会奖励过度切分）。

**这是最容易被专家一句话打穿的地方。**

## 五、实测数据：意图来源的可获得性

42 个会话上的投影可得性：

```
title 29 · plan 20 · outline 19 · goal 3 · todos 2
intent 2（52 组 · 2 转向 · 2 个会话有压缩）
```

**`goal` 只有 3 个会话有**——官方那套目标控制虽强，但**要求用户显式建目标**，
所以用的人少。而 `plan`(20) 与 `outline`(19) **几乎人人都有**，因为它们是自动的。

⇒ **这暗示一个方向**：把 `plan` / `outline` 当作**意图的隐含来源**，
而不是等用户去建 goal。3/42 → 20/42 是数量级差别。

## 五之二、评审 §4 的那条张力**不适用**（前提与实际不符）

评审 §4 指出：我建议"把 `plan` / `outline` 当意图来源"，但它们是**模型产出的
投影**，拿它们当来源等于换条路又问了一次模型，与"不问模型"相抵。
它给的出路是分层（当候选来源，要求关键项能在用户自己的发言里找到落点）。

**那条建议基于一个与实际不符的前提。** 实测两个投影的形状：

| 投影 | 实际形状 | 能当意图来源吗 |
|---|---|---|
| **`plan`** | `{"active": bool, "pending": bool}` | ❌ **只有两个布尔**——它不携带任何计划文本 |
| `outline`（即 `turnOutline`） | `[{turn, seq, prompt, response}]` | ✅ 但**我本来就在用它**——那是面板的数据源 |

⇒ `plan` 不是"模型写的计划"，它只是 **plan 模式的开关状态**。
拿它当意图来源无从谈起。"候选来源 + 落点校验"这套设计**没有作用对象**。

**而 `outline` 那一半的张力本来是不存在的**：面板显示的 prompt/response
**就是用户与助手的原话**，我们只是对它们做词法分组——没有"模型的自我叙述"
被继承进来。要防的污染是**检索/注入类**插件的问题（如 `topics-memory` 把
结论注入模型），不是展示类插件的问题。

## 六、由调研推出的三条建议（按价值排序）

**① ~~把 `plan` / `outline` 接进来当意图来源~~** —— **已否，见 §五之二**。
`plan` 只有两个布尔，不是计划文本。`outline` 本来就是数据源。

**替代：把 `goal/change` 的时间线用起来**（已做）。
官方 `goal` 投影**只有当前值，没有历史**；而我们 fold 出了"目标何时建立、
改过几次"。实测 `session-abcd1238`：`["26:create","27:complete","30:create",
"30:complete"]` → `goalOnset = 30`。**这是官方投影没有的信息。**

**② 分层要重新想，避开已拥挤的方向**

现在"概况层=组、详情层=回合"。而 `dsh-outline` / `dsh-conversation-navigator` /
`dsh-question-nav` 已经在做"问题列表 + 跳转/小地图"（3,000+/月）。
**我们该做它们做不到的**：组 → **该组在做的事**（派生目标），而不是又一棵问题树。

**③ 那条"基线编辑器"要么删、要么改定位**

现在它与官方 `dsh-command-goal` 重复且更弱。两个出路：
- **删掉**：把注意力收回到"展示派生的意图结构"这个独有面
- **改定位**：明确写成"**只影响本面板的观察基准，不约束 agent**"——
  与官方 goal 形成分工而不是竞争

## 七、一处必须记住的判断

**"意图控制"不是我们的位置。** 官方五包 + plan-mode + user-questions + permissions
已经把"约束 agent 做什么"做完了，而且有执行期权限检查、事件溯源、竞态防护——
那不是插件该重新发明的。

**我们的位置是"意图的观察面"**：不问模型、不需要用户先建目标、
从会话本身算出结构。这条位置有生态空缺，也有实测支撑。
