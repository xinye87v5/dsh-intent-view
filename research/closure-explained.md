# "闭包"是什么意思，以及它是不是该做的事

## 一句话

**闭包 = 挂一个具体节点时，把它的祖先也一起挂上。**

拿旅游那一版举（`travel-run3`）：

```
#2「时间上十一月中旬怎么样，会不会太冷」
  模型给的落点：出行时间与预算
  闭包之后：    出行时间与预算 + 京都五天行程框架      ← 补上了祖先
```

我提它的理由：同一份冻死水线连跑三次，**"层级风格"每次都不一样**——
有时整条祖先链一起挂，有时只挂最具体的那个：

| | 根收多少行 | 整链完整的回合 |
|---|---|---|
| travel-run1 | 3 | 4 / 30 |
| travel-run2 | 21 | 22 / 30 |
| travel-run3 | 3 | 4 / 30 |

而"**落在哪个具体任务**"三次高度一致（最具体落点一致率 98.9%）。
所以我想：把层级用一条确定性规则抹平，方差就没了。

## ⚠️ 但有一件事必须先说清楚

**闭包不是复现你认可的那一版。** 你认可的童话版是"模型自然的部分链"
（根收 14 行、平均每回合 2.23 个落点）；全量闭包会给根收 29 行、平均 3.06 个落点。
任何"规则化"都必然在某些行上与那一版不同——认可的是**分类对不对**，
不是每一行的落点个数。

## 四种做法（同一批实测数据，离线算的）

| 做法 | 每个回合带什么 | travel 三次的根收行数 | travel 平均落点数 | 是否三次一致 |
|---|---|---|---|---|
| 原样（模型给什么算什么） | 不定 | 3 / 21 / 3 | 1.20 / 2.03 / 1.20 | ✗ |
| (a) 全量闭包 | 根 + 全部中间层 + 具体 | 29 / 29 / 29 | 2.30 / 2.30 / 2.30 | ✓ |
| (b) 根 + 具体（去中间层） | 两级 | 29 / 29 / 29 | 2.07 / 2.07 / 2.07 | ✓ |
| (c) 大块 + 具体（根只当容器） | 根的下一级 + 具体 | 0 / 0 / 0（剥掉根后） | 1.37 / 1.37 / 1.37 | ✓ |
| (d) **只存最具体落点** | 具体 | 3 / 21 / 3 | ≈1.2 | ✓（一致率 98.9%） |

## 关键观察：**中间层的路径本来就在图里**

节点图（每个节点的 `parents`）**永远**记录了完整的层级。
所以"回合挂不挂中间层"这件事，**不携带任何图里没有的信息**——
想显示"项目 → 插画 → 第一页内容 → 这段对话"，从具体节点往上走 parents 就能算出来。

⇒ 于是有两种对称的做法：

- **fill（闭包）**：存的时候把祖先补进去，让数据本身就带路径；
- **strip（规范化）**：存的时候**只留最具体的那几个落点**，路径等要用时按图展开。

两者互逆。**strip 更好**，因为：

1. 它让存储最小、可幂等（跑两次结果一样），跨运行的层级方差**从数据里消失**；
2. 信息一点没少（路径可从图重算）；
3. 渲染想显示几层就显示几层——**这个选择不必现在定死**，
   更不该由模型每次采样决定。

（上面的 (d) 就是 strip。它的 travel 三次根收行数还写着 3 / 21 / 3，
是因为那一栏是"原样里含根的回合数"，不是 strip 后的；strip 后三次的
**最具体落点集合**一致率 98.9%。）

## 我改口的结论

原先我建议"直接启用闭包"。看完这组数，**改成建议 strip**：

- 流水线存：`最具体落点`（`specific()` 那个纯函数，去掉被同回合其它落点包含的祖先）；
- 渲染要路径时：`expandToChain()`（就是现在的 `closeUnderAncestors`）按需展开；
- 两个函数都已实现、都在 41 项离线断言里。

这样"要不要整条链"就从一个**每次采样都会跳的模型行为**，
变成一个**渲染时可选的纯函数**——这才是它该待的地方。

## ❓ 两个常见误解（都被问过）

**误解一：闭包是"给节点改名，让它带上母节点的名字"。**
不是。实测：闭包前后**节点名一个都没动、父子关系一个都没动**，
动的只有 `membership`（回合挂在哪）：

```
#18「岚山小火车要提前订票吗」
   原样  ： 第三天安排 → 岚山小火车订票
   闭包后： 第三天安排 → 每日行程安排 → 京都五天行程框架 → 岚山小火车订票
```

"名字带路径"是**显示**的事（面包屑），随时能从 `parents` 渲染出来，不必存。

**误解二：闭包让子节点"绕过某些层级"。**
不是绕过，是**把每一级都补上**；于是效果上**任何一级祖先都成了检索入口**——
查"挂在 X 下的回合"会连带取到 X **所有后代**上的回合，即检索变成**子树聚合**。

两种取法实测等价（`travel-run3`，11 个任务节点逐个比）：

| 取法 | 怎么问 | `京都五天行程框架` | `每日行程安排` | `第一天安排` |
|---|---|---|---|---|
| 闭包（预物化） | 看"挂在 X 下的回合" | 29 | 11 | 1 |
| strip + 子树查询 | 取"X 及其全部后代的回合" | 29 | 11 | 1 |

⇒ 这是**纯实现选择**：存的时候算好，还是查的时候算。检索结果一样。
本项目建议后者（strip + 查询时聚合）：存得少、无冗余、且采样方差从数据里消失。

**还没遇到过的一种情形**：一个节点有**多个母节点**（真 DAG 分支）。
`travel` 三次运行里都没有；一旦出现，闭包会把**每一条父链**都补上——
那正是使用者最早那句"同个对话存了几个任务的内容，几个任务下都放"落地的地方。
