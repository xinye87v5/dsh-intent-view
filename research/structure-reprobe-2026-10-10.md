# 复跑任务结构流水线：材料换成"宿主折叠那份"之后（3098 真模型）

> 补 `projection-slimming-2026-10-10.md` 里写明的那件"没验"的事：
> 客户端送进 `/api/intent.structure` 的材料换了来源（从官方 `turnOutline` 的短截断
> 换成宿主折叠的 `intent.turns[].prompt`，最多 400 字），**当时没再花调用跑真模型**。
> 这份是那次复跑的结果。

## 怎么跑的

新探针 `tools/probes/structure-via-host.mjs`：把材料打给**真正发出去的那条路**
（3098 上的 `/api/intent.structure`，cookie 认证），不是自己拼提示词——
本项目吃过"研究里验证过的 ≠ 插件里跑着的"的亏。

材料口径**直接 import 宿主那一份**（`lib/host/intentProjection.js` 的 `preview`，
本轮为它补了 export 与 4 条断言），不在探针里重抄规则。仍然如实标注两点差别：

1. 联系方式打码（`session-turns.mjs` 的 `maskPrompt`，只影响姓名/电话/邮箱）；
2. 会话日志里同一回合多条用户消息时的聚合方式取自 `session-log.mjs`。

所以它证明的是"**400 字口径的材料能跑通、结果与覆盖都合理**"，
不是"字节级等于浏览器送的那一份"。探针自带 5 条判据（有节点 / 有根 / 覆盖 ≥90% /
节点都有标题 / 归属里的 id 都存在）。

- **真 DAG 的两半都出现了**：多归属回合（`f1fa55a8` 2 个、`d5b0e76c` 6 个）与
  3 条线并存的会话（`c13af336`）。此前"一个回合挂在两个任务上"只在合成语料里见过，
  现在真实会话里也有了——`d5b0e76c` 的 `#2` 同时挂在"调研 jev 模型契合"与

## 这份**不能**说明什么

- **一次一份样本**，不是分布。节点数在重跑间的方差没有量过（此前量过的是
  标签/覆盖那些指标，见 `task-structure-e2e-2026-10-10.md`）。
- **没验浏览器与探针的材料字节级一致**（上面第 1、2 点差别）；要验那个得从页面里
  抓请求体，本轮没做。
- `f1fa55a8` 只取了前 60 回合（它共 139 回合）；压缩回合那一档没专门造样本。
  超长会话这一档已经补上了（`f1cd07a6` 377 回合，见下面那节），但**只此一场**。

## 复跑方法

```bash
# 取 cookie（3098 的 URL 带 token，见 ~/.dsh/restart-3098-*.log）
curl -s -c /tmp/cj.txt -o /dev/null "http://127.0.0.1:3098/?token=<token>"

node tools/probes/structure-via-host.mjs --session f1fa55a8 --max 60 \
  --url http://127.0.0.1:3098 --cookie /tmp/cj.txt --hash <指纹>
```

不给 `--hash` 就按分钟生成（冷跑、真花调用）；给同一个值再跑应当回 `cached: true`。

## 超长会话：`f1cd07a6` 377 回合（一场）

这一档原本写在"没验"里，现在补上。**一场，不是分布。**

| 项 | 值 |
|---|---|
| 材料 | 377 条，合计 12.2 KB（avg 32 字，2 条到 400 字上限） |
| 调用 | **33 次**（建结构 1 + 分批归属 30 + 判整理 1 + 根裁定 0 + 补问 1） |
| 批次 | 30（`firstWindow:20`、`chunk:12`） |
| 耗时 | **41.7 秒**（单次调用约 1.3 秒，与短会话同量级） |
| 节点 / 线 | **225 个节点 / 1 条线**（单线，项目根 `小说创作上下文`） |
| 覆盖 | **377/377**（承接继承 11、补问 9） |
| 多归属回合 | 10 个（#9、#22、#117、#128、#262、#285、#286、#290、#296、#325） |
| `adjudication` | `no-roots` ——**不是失败**：建结构那一步就只产出了 1 个顶层节点（<2），没有可裁定的 |

**覆盖与线都守住了**：377 个回合一个没漏，承接继承 + 补问把最后 20 个补齐
（与短会话同一套机制）。**没有出现"长会话跑不动"**：33 次调用只花 41.7 秒。

### 但形状退化了：225 个节点里 171 个只收 1 个回合

把响应落盘之后离线量（`tools/probes/.out/structure-f1cd07a6-reprobe-f1cd377-a.json`）：

| 形状指标 | 值 |
|---|---|
| 深度分布 | 项目根 1 个（深度 0）→ 30 个（深度 1）→ **193 个（深度 2）** → 1 个（深度 3），最大深度 **3** |
| id 前缀 | `t##` **210 个** / `n##` 15 个 |
| 每个节点收几个回合 | 收 1 个的 **171 个**、收 0 个的 0 个、收 ≥5 个的 16 个 |
| `kind` | 225 个全是 `task`（没有 `aside`） |

读法：**分批归属那一步几乎每遇到"对不上现有节点"的回合就新建一个节点**
（`t##` 是那一步建的），30 批下来节点从 15 个涨到 225 个；而**建结构只给了 15 个**。
结果是一棵"一个项目根 + 30 个中层 + 193 个单回合节点"的很宽的树——
在面板上就是 225 个可折叠节点，很难读。

**这一条我只报事实，不断言原因**：判整理那一步到底做了什么，我没有证据——
它没有自己的日志行，探针也没抓模型原始回复。所以"是不是判整理的合并被长节点表撑住了"
**属于猜测**，要么去抓一次回复，要么做 A/B（关掉分批/关掉判整理各跑一场）才知道。
下一轮可以做的候选：

1. 抓一次 `判整理` 的原始回复，看它给了几个 op（成本 1 次调用）；
2. 量"节点数 / 回合数"这条曲线（多场会话）——1:1.7 这个比例是否普遍；
3. 真要做收敛，方向是给分批归属加一条"优先挂到已有节点"的约束，或让判整理分批跑。
